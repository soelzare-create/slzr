# نقشه داده داران‌ایکس

هر جدول یک نوع اطلاعات را نگه می‌دارد. دو نکته کلیدی بلوپرینت:

1. کالاها دو نوع‌اند: **سریال‌دار** و **بدون‌سریال** — ولی همه در یک جدول
   `stock_items` نگه داشته می‌شوند (سریال اختیاری).
2. هر **فاکتور** صادرکننده مشخص دارد (`invoices.issuer_id`) برای محاسبه پورسانت.

---

### `users` — کاربران (تیم شرکت)

| فیلد               | نوع    | توضیح                                       |
| ------------------ | ------ | ------------------------------------------- |
| id                 | PK     | شناسه                                        |
| name               | متن    | نام                                          |
| role               | enum   | مدیر/فروش/فنی/انباردار/حسابدار               |
| password_hash      | متن    | رمز ورود (bcrypt)                            |
| phone              | متن    | شماره تماس (شناسه ورود، یکتا)                |
| address            | متن    | آدرس                                         |
| emergency_contact  | متن    | تماس اضطراری                                 |
| is_active          | بولی   | فعال/غیرفعال (حذف نرم)                        |

### `parties` — طرف‌حساب‌ها (مشتری و/یا تأمین‌کننده)

یک رکورد واحد برای هر طرفی که با او کار می‌کنیم. می‌تواند مشتری باشد، تأمین‌کننده،
یا **هر دو** — بدون تکرار. مانده‌ی خالص هر طرف از همین‌جا محاسبه می‌شود.

| فیلد            | نوع   | توضیح                              |
| --------------- | ----- | ---------------------------------- |
| id              | PK    | شناسه                               |
| name            | متن   | نام شخص یا سازمان                    |
| phone           | متن   | شماره تماس                          |
| address         | متن   | نشانی                               |
| is_customer     | بولی  | نقش مشتری دارد                      |
| is_supplier     | بولی  | نقش تأمین‌کننده دارد                |
| contact_date    | تاریخ  | تاریخ آشنایی (برای نقش مشتری)       |
| referral_source | متن   | مدل آشنایی (برای نقش مشتری)         |

> قانون: هر طرف‌حساب باید حداقل یک نقش داشته باشد. جدول `activities` با
> `customer_id` به همین جدول (نقش مشتری) وصل می‌شود و `purchases`
> با `supplier_id` (نقش تأمین‌کننده).

### `party_contacts` — افراد رابطِ سازمانِ طرف‌حساب

هر طرف‌حساب یک سازمان است و می‌تواند **چند فرد رابط** داشته باشد؛ هرکدام با یک
**سمت** مشخص، تا در آینده بتوانیم با هر بخش سازمان (خرید، مالی، فنی، …) تماس
بگیریم. هر رکورد نگه می‌دارد که کدام کاربرِ ما آن را ثبت کرده است.

| فیلد           | نوع  | توضیح                                            |
| -------------- | ---- | ------------------------------------------------ |
| id             | PK   | شناسه                                             |
| party_id       | FK   | طرف‌حساب (با حذف طرف‌حساب، افرادش هم حذف می‌شوند)  |
| name           | متن  | نام فرد                                           |
| phone          | متن? | شماره تماس                                        |
| position       | enum | سمت (اجباری): مدیرعامل/خرید/فروش/مالی/فنی/انباردار/کارشناس/سایر |
| created_by_id  | FK   | کاربری که این فرد را ثبت کرده                     |

> «سمت» از یک فهرست کنترل‌شده انتخاب می‌شود و درج آن الزامی است. در CRM، هنگام
> باز کردن هر مشتری، فهرست افراد رابط (سمت + نام + شماره) زیر آن نمایش داده می‌شود.

### `stock_items` — ردیف‌های انبار (یک جدول واحد)

هر ردیف یا **تک‌کالای سریال‌دار** است (سریال + وضعیت) یا یک **حرکت کالای
بدون‌سریال** (جهت + مقدار). دو جدول قبلی (`unit_items` و `inventory_movements`)
در همین ادغام شدند.

| فیلد          | نوع   | توضیح                                        |
| ------------- | ----- | -------------------------------------------- |
| id            | PK    | شناسه                                         |
| model_id      | FK    | مدل کالا                                      |
| serial_number | متن?  | شماره سریال (فقط سریال‌دار؛ یکتا)             |
| quantity      | عدد   | مقدار (سریال‌دار=۱؛ بدون‌سریال=مقدار حرکت)    |
| status        | enum? | وضعیت تک‌کالا: انبار/فروخته/نصب‌شده/خراب      |
| direction     | enum? | جهت حرکت بدون‌سریال: ورود/خروج                |

> **موجودی هر کالا** محاسبه می‌شود: سریال‌دار = تعداد ردیف‌های «انبار»؛
> بدون‌سریال = مجموع ورودها − مجموع خروج‌ها.

### `invoices` — فاکتورها

هر فاکتور به یک فعالیت وصل است ولی اقلامش را خودش نگه می‌دارد. یک فعالیت می‌تواند
چند پیش‌فاکتور و چند فاکتور نهایی داشته باشد.

| فیلد         | نوع  | توضیح                          |
| ------------ | ---- | ------------------------------ |
| id                  | PK   | شناسه                           |
| activity_id         | FK   | فعالیت (پوشهٔ دسته‌بندی)         |
| issuer_id           | FK   | صادرکننده (برای پورسانت)         |
| kind                | enum | پیش‌فاکتور/فاکتور نهایی          |
| total_amount        | عدد  | مبلغ کل (از جمع اقلام همین فاکتور) |
| status              | enum | پرداخت‌شده/معوق/پرداخت‌نشده      |
| settlement_due_date | تاریخ | تاریخ تصفیه حساب                 |
| source_proforma_id  | FK?  | اگر از روی یک پیش‌فاکتور ساخته شده |

> **پیش‌فاکتور:** `kind` تعیین می‌کند پیش‌فاکتور است یا فاکتور نهایی. پیش‌فاکتور
> اثری روی انبار/حساب ندارد و آزادانه قابل حذف است؛ فاکتور نهایی هنگام صدور، کالای
> ردیف‌های متصل به انبار را خارج و درآمد را ثبت می‌کند.

### `invoice_items` — اقلام فاکتور

هر ردیف یک کالا یا خدمت است. `product_model_id` اختیاری است؛ اگر پر شود، هنگام صدور
فاکتور نهایی از موجودی همان کالا کم می‌شود (ردیف‌های خدمت/شرح آزاد اثری روی انبار ندارند).

| فیلد             | نوع  | توضیح                                   |
| ---------------- | ---- | --------------------------------------- |
| id               | PK   | شناسه                                    |
| invoice_id       | FK   | فاکتور                                   |
| description      | متن  | شرح ردیف (نام کالا یا خدمت)              |
| product_model_id | FK?  | کالای انبار (اختیاری — برای کسر موجودی)  |
| quantity         | عدد  | تعداد / مقدار                           |
| unit_price       | عدد  | قیمت واحد                               |

## جریان نمونه «فروش یک کالا»

```
فروشنده کالا را انتخاب می‌کند
   → فاکتور ساخته می‌شود            (invoices)
      → پیام به انبار: «یکی کم کن»   (stock_items: سریال→sold / حرکت خروج)
      → پیام به حسابداری: «ثبت کن»    (financial_documents type=income)
```

هر بخش فقط کار خودش را انجام می‌دهد؛ ارتباط از راه پیام است، نه دست‌بردن مستقیم.

## جریان نمونه «خرید یک کالا» (قرینهٔ فروش)

```
انباردار تأمین‌کننده و کالا را انتخاب می‌کند
   → سند خرید ساخته می‌شود           (purchases)
      → پیام به انبار: «یکی اضافه کن»  (stock_items: سریال جدید / حرکت ورود)
      → پیام به حسابداری: «خرج ثبت کن»  (financial_documents type=expense, party_id)
```

## مانده‌ی هر طرف‌حساب

`مانده = مجموع دخل (فروش به او) − مجموع خرج (خرید از او)` — چون هر دو سمت به یک
رکورد `parties` وصل‌اند، یک عدد واحد برای هر طرف به دست می‌آید.
